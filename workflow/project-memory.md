### 2026-09-10 — PRODUÇÃO: OOM/crash-loop por `queryCollection('content')` numa collection NÃO declarada
**Context:** Site em produção (`acessocatolico.com.br`) ficou lento e dando `502`; reiniciar o Caddy não resolvia. `docker logs acessocatolico_app` mostrava `FATAL ERROR: Ineffective mark-compacts near heap limit — JavaScript heap out of memory` com `RestartCount` subindo. Sob carga leve o container ia de ~45MB a ~2GB de heap, GC entrava em thrashing (pausas mark-compact de 3,5s → lentidão e `504`) e então o processo morria e o Docker reiniciava (→ `502`).
**Gotcha:** O catch-all `app/pages/[...slug].vue` chama `queryCollection('content').path(route.path).first()`, mas **a collection `content` nunca foi declarada** em `content.config.ts` (só existia `blog`). Consultar uma collection inexistente faz o `@nuxt/content` v3 buscar uma tabela SQLite que não existe e **lançar erro em CADA URL não-casada** — ou seja, em todo request `404` de bot/scanner/link quebrado, que é tráfego constante em qualquer site público. Cada um desses erros dentro do `useAsyncData` + a renderização do erro fatal vazava alguns MB de heap por request; em minutos batia no teto (~2GB do V8) e derrubava o processo. Reproduzido num container isolado (fora do Caddy): ocioso estável a 33MB; 800 requests de `404` (path fixo OU distinto) → 2,16GB e **crash**. Rotas `200` (home/blog/loja) NÃO vazam — o GC recupera; só o caminho que consulta a collection inexistente + `throw createError(404, fatal:true)` vaza. O `error.vue` é leve (sem query), não é ele. **Comparação útil:** `caiohenvieira.com.br` usa a mesma stack Nuxt Content e é imune porque NÃO tem catch-all na raiz — URLs desconhecidas caem no 404 nativo do Nuxt, sem query de conteúdo.
**Resolution:** Declarada a collection `content` faltante em `content.config.ts` (`type: 'page'`, `source: { include: '**', exclude: ['blog/**'] }` — exclui os posts para não duplicar a collection `blog` tipada). Agora um `404` faz uma query válida que retorna `null` de forma barata em vez de lançar erro. Validado no probe com o mesmo flood que crashava a versão antiga: pico de 252MB, GC derruba pra ~88MB, container de pé, e as 800 reqs terminam em ~4s (antes >120s). Deploy: rebuild da imagem + `docker compose up -d --force-recreate`. Pós-deploy em produção: `/` 200 em 0,44s, `/blog` 0,09s, `/loja` 0,07s, `404` limpo em 0,09s; memória ~80MB, CPU ~0%, `RestartCount=0`. **Lição:** ao usar `queryCollection('X')`, garantir que `X` exista em `content.config.ts` — collection inexistente não é erro de build/tipo silencioso benigno, é um vazamento de heap em produção proporcional ao tráfego 404. Melhoria opcional pendente: `mem_limit` no compose + `NODE_OPTIONS=--max-old-space-size` coerente, para que um vazamento futuro degrade com restart rápido em vez de thrashing prolongado a 2GB.

### 2026-09-09 — Build de produção (step 52): singleton Prisma quebrava o prerender sem `DATABASE_URL`
**Context:** `npm run build` em `portal/` sem `.env` (só `.env.example`) — build não pode exigir banco vivo.
**Gotcha:** O singleton `server/utils/prisma.ts` instanciava o client **no carregamento do módulo** (`export const prisma = ... ?? createPrismaClient()`). Como o bundle do Nitro avalia esse módulo já na **inicialização do prerenderer**, `createPrismaClient()` lançava `DATABASE_URL não definida` ANTES de qualquer handler rodar — o `try/catch` resiliente dos endpoints (que só envolve a *query* `findMany`/`groupBy`) nunca era alcançado, e o build inteiro caía com `ERROR DATABASE_URL não definida` em "Initializing prerenderer". Ou seja: a resiliência cobria "banco inacessível", mas NÃO "sem env no import".
**Resolution:** Tornar o singleton **preguiçoso**: `prisma` agora é um `Proxy` que só chama `createPrismaClient()` no primeiro acesso a uma propriedade (`prisma.product...`), via `getPrismaClient()` (cacheia em `globalThis.prisma` só em dev, pro HMR). Assim o import nunca quebra; o erro de env/banco só surge na primeira query, DENTRO do try/catch, que devolve `{ data: [] }`. Build passa (`EXIT=0`, "Prerendering 1 routes" = só o SQL dump do @nuxt/content, **0 páginas HTML** em `.output/public` → home/loja/blog seguem SSR, buscando produtos em tempo de requisição, não de build). O seed (`prisma/seed.ts`) NÃO usa esse singleton (instancia o seu próprio client), então não foi afetado. A WARN de `h3.mjs` ("H3Error... never used") vem do `@nuxt/nitro-server` interno — ruído, não é do nosso código.

### 2026-09-09 — Endpoint de categorias (step 43): `groupBy` para categorias com contagem
**Context:** Criar `portal/server/api/products/categories.get.ts` retornando categorias ativas com contagem (chips de filtro).
**Gotcha:** `category` é string livre (sem tabela de categorias), então para listar distintas com contagem usa-se `prisma.product.groupBy({ by: ['category'], where: { active: true }, _count: { _all: true }, orderBy: [...] })`. Dois pontos de tipagem do Prisma 7: (1) no `orderBy` de um `groupBy`, ordenar por contagem é `{ _count: { <campo>: 'desc' } }` (referenciando um campo do `by`, ex. `category`), não `{ _count: 'desc' }`; (2) o valor da contagem lido é `group._count._all` (por causa de `_count: { _all: true }`). Segui o mesmo padrão de resiliência do `products/index.get.ts`: try/catch com `console.error` no servidor e fallback `{ data: [] }` (200), sem vazar internals.
**Resolution:** Retorna `{ data: [{ name, count }] }` ordenado por contagem desc, depois nome asc. Validado com `npx nuxi prepare` (de `portal/`), `eslint` (limpo) e `tsc --strict` (sem erro de tipagem no groupBy). Não testado contra Postgres real neste ambiente.

### 2026-09-09 — Prisma seed (step 41): script standalone precisa do próprio adapter + `process.loadEnvFile()`

### 2026-09-09 — Breakpoints são literais, não var()
**Context:** Media queries em componentes (ex.: nav inline no desktop).
**Gotcha:** Custom properties não funcionam dentro de media queries. Os `--bp-*` são só CONVENÇÃO documentada em `app/assets/css/main.css`.
**Resolution:** Usar os valores literais em `min-width`: `--bp-md` = `48rem`, `--bp-lg` = `64rem`, `--bp-sm` = `30rem`. Mobile-first sempre.

### 2026-09-09 — @nuxt/fonts detecta famílias em custom properties e self-hospeda
**Context:** Configurar as webfonts (Spectral, Figtree, JetBrains Mono).
**Gotcha:** As famílias são referenciadas via `var(--font-*)` no reset; os nomes literais só aparecem nos tokens (`--font-display: 'Spectral'...`).
